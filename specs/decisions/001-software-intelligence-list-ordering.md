# DR-001: 软件情报列表的标识排序

## 状态

已接受
本条已由 [DR-002](002-software-intelligence-list-ordering-revision.md) 部分修订。
修订范围包括列表覆盖范围、漏洞列表主排序和生命周期排序。

## 背景

- 软件情报详情包含概览、版本发布、生命周期、漏洞和采集日志五类列表。
- 本决策中的概览指软件详情中的概览标签页。
- 这些列表目前分别按时间、优先级或数据库返回顺序排列，没有统一的标识排序规则。
- 发布版本号和生命周期周期按文本比较时，`1.10` 会排在 `1.9` 之前，与版本先后相反。
- 多个记录具有相同时间、相同优先级或相同状态时，列表没有稳定的同值排序键。
- 数据库 UUID 是随机标识，不表达业务先后，也不应作为用户可见的列表编号。
- 结果是同一份数据在重复请求、分页边界或不同页面之间可能呈现不同的标识顺序。

## 决策

### 排序原则

- 列表顺序应由服务端一次确定，客户端只做筛选和分组，不改变记录的相对顺序。
- 每个列表应同时声明主排序键和同值排序键，最终以不可变的记录标识兜底。
- 用户可见的标识应按业务语义比较，内部 UUID 只用于稳定兜底，不作为业务编号展示。
- 版本号和周期使用自然数值比较，公告编号使用前缀加数值段的自然比较，禁止直接按普通文本比较。
- 同值排序键只保证稳定和可复现，不改变主排序键表达的产品含义。

### 列表顺序

| 列表 | 主排序 | 同值排序 |
| --- | --- | --- |
| 概览 · 安全状态 | 版本影响：确认受影响 → 可能受影响 → 版本信息不足 → 不受影响 | 优先级 → 上游发布时间倒序 → 公告编号自然倒序 → 记录标识 |
| 概览 · 最近版本 | 上游发布时间倒序，缺失时使用首次发现时间 | 版本号自然倒序 → 记录标识 |
| 版本发布 | 上游发布时间倒序，缺失时使用首次发现时间 | 版本号自然倒序 → 记录标识 |
| 生命周期 | 当前周期优先 | 周期自然倒序 → 记录标识 |
| 漏洞 | 优先级 P0 → P1 → P2 → P3 | 上游发布时间倒序 → 公告编号自然倒序 → 记录标识 |
| 采集日志 | 开始时间倒序 | 记录标识 |

- 概览中的安全状态与最近版本分别遵循漏洞列表和版本发布列表的同一条排序规则。
- 生命周期中的当前周期固定在其软件分组的第一行，其余周期按自然顺序倒序。
- 采集日志没有面向用户的业务编号，记录标识只用于同一开始时间下的稳定兜底。
- 记录标识不得覆盖主排序键的业务含义，也不得在界面中替代版本号、周期或公告编号。

### 最小可验证版本

- 只调整上述五类列表的排序，不新增排序控件、筛选条件、分页能力或数据库字段。
- 修复版本号和周期被按文本比较的问题，并为所有同值情况补上稳定兜底。
- 保持现有日期倒序、优先级顺序、影响等级和当前周期优先的产品语义不变。
- 同一份数据重复加载、滚动加载或跨页面查看时，标识顺序保持一致。
- 不改变列表中的字段、计数、空状态和交互。

### 验证口径

- 给定同一发布日期，版本发布列表应把 `1.10.0` 排在 `1.9.0` 之前。
- 给定同一软件，生命周期列表应把周期 `1.10` 排在 `1.9` 之前。
- 给定同一优先级和同一发布时间，漏洞列表应按公告编号自然倒序排列，例如 `CVE-2026-1000` 在 `CVE-2026-999` 之前。
- 给定同一开始时间，采集日志应保持稳定顺序，重复请求不得交换行位置。
- 对同一快照连续请求两次或跨越接口返回上限时，记录顺序应完全一致。
- 客户端筛选和日期分组后，记录在组内和组间的顺序应与服务端排序一致。

## 影响

- 用户看到的版本、周期、公告编号和采集记录顺序稳定且符合业务语义。
- 同一软件在概览、版本发布、生命周期和漏洞页面之间使用一致的排序规则。
- 分页、筛选和重复加载不会因为同值记录换位而出现重复或遗漏的错觉。
- 内部 UUID 不再被误认为可排序的业务编号。
- 代价是五类列表都需要明确声明同值排序键，并为自然标识比较补充测试。
- 不包含用户自定义排序、排序表头、优先级规则调整、排序字段持久化和界面重设计。
