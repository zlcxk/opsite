# Opsite 技术知识质量标准

版本：1.0  
生效日期：2026-10-31  
适用范围：技术地图中所有带 Markdown 文档的技术节点（Kubernetes、Prometheus 及后续领域）

## 1. 目的

这份标准解决三个问题：

1. 文档不能只有名词堆砌，必须解释“它是什么、为什么存在、怎么工作、何时会坏”。
2. 文档必须能追溯到官方来源，版本边界要写清楚。
3. 内容状态和验证记录必须可信，不能被普通编辑或 Seed 覆盖破坏。

标准只约束知识内容的质量和维护流程，不改变技术地图的树形布局、架构视图、颜色、字体、间距、卡片风格和交互习惯。

## 2. 内容分级

### L1 定位卡

- 长度约 80–150 字。
- 说明对象是什么、解决什么问题、和相邻概念的区别。
- 允许作为草稿，不能标为“已完善”。

### L2 机制文档

- 正文不少于 1500 字。
- 必须包含：定位、设计原理、工作机制、关键配置、常见问题、技术关联、参考资料。
- 至少解释一个“为什么这样设计”，不能只列字段。
- 至少给出一个可验证的失败场景或排查方向。
- 至少 2 个可访问的官方来源。

### L3 深度文档

- 正文不少于 3000 字。
- 在 L2 基础上，完整覆盖：
  - 组件在架构中的位置和数据流；
  - 关键对象关系与生命周期；
  - 版本差异和适用边界；
  - 至少 5 个常见问题或限制；
  - 与其他技术节点的有依据关联；
  - 官方文档中容易误解的细节。
- 第一批五个 Kubernetes 节点按 L3 标准执行。

## 3. 固定章节结构

除非节点类型确实不适用，文档按以下顺序组织：

1. **技术定位**：是什么、位于哪一层、解决什么问题、不适合什么场景。
2. **设计原理**：为什么这样设计，关键抽象和取舍是什么。
3. **工作机制**：对象如何创建、状态如何流转、组件如何协作。
4. **关键配置与实践**：影响行为的字段、默认值、生产建议。
5. **常见问题与限制**：故障表现、根因、边界和容易误解之处。
6. **技术关联**：上下游组件、对象关系、替代方案。
7. **参考资料**：官方文档优先，链接必须可访问。

标题层级保持两级以内（`##` / `###`），代码块使用 `~~~` 围栏，避免破坏既有 Markdown 渲染。

## 4. 准确性规则

- 只写能被官方文档、发布说明、RFC、源码或可复现实验支持的事实。
- 区分“确定事实”“版本相关行为”“作者判断”。判断性内容要标明依据或适用条件。
- 不虚构生命周期、版本号、GitHub 仓库、漏洞映射、默认值或性能数字。
- 默认值必须来自对应版本文档；无法确认时写“取决于实现/配置”，不要猜。
- 版本边界必须写进“适用版本”字段和正文。跨版本行为变化要明确指出。
- 不使用“永远”“绝对不会”等无法证明的表述。
- 安全相关内容必须说明前提，不把实验室结论直接写成生产建议。

## 5. 来源标准

优先级：

1. 项目官方文档（kubernetes.io、prometheus.io 等）。
2. 官方发布说明、CHANGELOG、KEP、RFC。
3. 官方源码和 API 参考。
4. 高质量工程博客或厂商文档，仅作为补充，不作为唯一依据。

要求：

- `docsUrl` 指向该节点的官方入口。
- `referenceLinks` 至少 2 条，建议 3–4 条，全部为 `https://`。
- 每条资料链接在提交前检查 HTTP 状态和内容主题是否匹配。
- 参考资料不得指向搜索页、失效页面或与主题无关的首页。
- 引用具体版本行为时，优先使用对应版本文档，而不是最新版本文档。

## 6. 内容状态与验证语义

状态定义：

- **missing（待补充）**：没有 Markdown 正文。
- **draft（草稿）**：有正文，但未经人工验证。
- **needs_review（待复核）**：有正文，已知需要重新核对。
- **complete（已完善）**：正文经过人工验证，并记录了验证所依据的版本。

硬性规则：

1. 普通创建和 PATCH 不能把状态设为 `complete`。
2. 普通 PATCH 不能写入 `verifiedVersion` 或 `contentVerifiedAt`。
3. 只有显式“验证知识”操作可以设置 `complete`。
4. 验证必须同时满足：
   - Markdown 正文非空；
   - 验证版本非空；
   - 验证操作不修改正文。
5. 验证成功后记录 `contentVerifiedAt` 和 `verifiedVersion`。
6. 编辑已完善文档的正文时，状态自动降级为 `draft`。
7. 降级后保留上一次验证时间和版本，作为历史记录展示为“上次验证”，不得继续暗示当前内容已验证。
8. 清空正文后状态为 `missing`，无论调用方请求什么状态。

前端状态选择器不得提供可选的 `complete`；当前为 `complete` 时只能展示为不可选状态，并提示通过验证操作维护。

## 7. 关系标准

关系必须满足：

- 有明确依据，能说清“为什么这两个节点相关”。
- 方向语义一致：
  - `contains`：整体包含部分；
  - `depends_on`：源在运行或语义上依赖目标；
  - `implements`：源实现目标抽象；
  - `alternative`：两者可互相替代；
  - `related`：存在重要关联，但不存在强依赖或包含。
- 不重复创建同一对节点的同一语义关系。
- 修改已有关系类型前，必须记录原值、新值、依据和迁移条件。
- 迁移只能匹配完全一致的原记录（id、source、target、旧类型），不得批量改写用户创建或修改过的关系。
- 关系修正不得删除其他关系或节点。

## 8. Seed 与数据安全

- Seed 只填补空字段，不覆盖用户已有内容。
- 合并逻辑必须正确处理 `undefined`、`null` 和空字符串：
  - `undefined` 表示“本次未提供”，不修改；
  - `null` / 空字符串表示“明确为空”，不得被当成有效内容写入；
  - 空字符串不得触发字段覆盖。
- 内容修订采用“旧内容哈希”门控：
  - 只有当库中 Markdown 的 SHA-256 与上一版权威内容完全一致；
  - 且状态仍为 `draft`；
  - 且没有验证时间；
  - 才允许替换为新版本。
- 用户编辑过、验证过或状态已变化的文档一律不替换。
- 数据迁移必须向前兼容：新代码能读取旧数据库，旧数据不会因升级丢失。
- 不删除技术节点、软件、个人笔记或用户关系。
- 不修改既有技术节点 ID。
- 所有迁移先在临时测试数据库中验证，再进入实际数据目录。

## 9. 写作与可读性

- 一段只讲一个观点，避免长句堆叠。
- 先给结论，再解释机制和例外。
- 术语首次出现时给出中文解释；同一文档内保持一致。
- 不使用空泛的“非常重要”“极大地提升”。
- 配置示例只保留理解机制所需的字段，避免复制整份生产清单。
- 表格用于对比，不用于堆砌长段落。
- 代码、字段名和命令保持原样，不翻译。

## 10. 验收清单

单篇文档：

- [ ] 定位、原理、机制、配置、问题、关联、参考七部分齐全。
- [ ] 达到对应等级的字数和深度。
- [ ] 适用版本明确，版本差异有说明。
- [ ] 至少 2 条官方来源，链接可访问。
- [ ] 没有无法证实的默认值、版本或仓库信息。
- [ ] 至少一个失败场景和排查方向。
- [ ] 与相邻节点的关系有依据。

系统行为：

- [ ] 创建或普通 PATCH 设置 `complete` 会被拒绝。
- [ ] 普通 PATCH 写入验证版本会被拒绝。
- [ ] 验证缺少正文或版本会被拒绝。
- [ ] 验证成功写入版本和时间，正文不变。
- [ ] 编辑已完善文档后降级为草稿，并保留历史验证记录。
- [ ] 前端无法通过状态下拉框绕过验证。
- [ ] Seed 不覆盖用户内容，哈希门控只替换未改动的旧版本文档。
- [ ] 关系迁移只命中精确旧记录。
- [ ] 自动化测试、前端构建、服务端构建和 Docker 构建通过。

## 11. 分批推广流程

1. 选择同一领域、互相有关联的 3–5 个节点作为一批。
2. 先审计官方来源和现有关系，记录需要修正的项。
3. 按本标准重写文档，标记内容修订版本和旧内容哈希。
4. 修正关系，提供可追溯迁移记录。
5. 在测试数据库验证 Seed 合并、状态流转和关系迁移。
6. 运行全部测试与构建。
7. 人工验收本批文档的可读性、准确性和关联完整性。
8. 验收通过后，下一批沿用同一标准；未通过不得批量推广。

第一批（Pod、Deployment、Service、Scheduler、Controller Manager）的验收记录见 [first-batch-verification.md](./first-batch-verification.md)。
